# 功能优化与备份工作流

本文档约束淘宝主图工作台后续每次功能优化的记录、验证和 Git 备份方式。目标是让任何一次改动都能回答：改了什么、依赖/模型是否变了、如何验证、能否安全回退。

## 1. 开始前

1. 在项目目录执行 `git status --short --branch`，确认是否存在他人未提交改动；不要 reset、checkout、clean 或覆盖这些改动。
2. 查看 `PROJECT_LOG.md` 的已知问题和最近变更，明确本次目标与不在范围内的事项。
3. 若涉及模型或依赖，先记录旧版本、模型文件来源/许可证、预计磁盘与显存需求。

## 2. 实现与验证

- 小步修改，优先保持本地离线和人工审核门禁；不要把生成结果或凭据写入仓库。
- 代码变更至少做适配的静态检查；API 变更至少启动服务并检查 `/api/health`、`/api/models` 或受影响端点；前端变更至少完成一次从输入到受影响阶段的浏览器冒烟验证。
- 模型下载、GPU、背景生成等重量操作若未执行成功，必须明确标记“未验证/环境受限”，不能写成已通过。
- 检查 `runtime/`、虚拟环境、日志和 PID 文件没有被加入暂存区；大模型文件只记录来源和校验信息，不提交二进制。

## 3. 完成后更新记录

在 `PROJECT_LOG.md` 的“变更记录”追加一节，使用以下模板：

```markdown
### YYYY-MM-DD · 简短标题

- 变更：
- 影响范围/兼容性：
- 模型与依赖：无变化；或列出包版本、模型版本、来源和许可证。
- 验证：命令/页面操作、结果、未覆盖项及环境限制。
- Git：<commit hash>（提交后填写）。
```

若功能引入新的已知问题、数据格式或运行步骤，同步更新项目记录和 README。

## 4. 安全 Git 备份

1. 再次运行 `git status --short --branch`，确认只包含本次目标和明确要备份的项目文件。
2. 使用路径限定的 `git add -- <files>`，不要使用 `git add .`；排除 `runtime/`、`.venv*/`、`*.log`、`*.pid` 和任何凭据/大模型文件。
3. 用 `git diff --cached --check` 和 `git diff --cached --stat` 检查空白错误及提交范围。
4. 创建描述性提交，例如 `git commit -m "docs: record project workflow"` 或 `git commit -m "feat: ..."`。
5. 记录 `git rev-parse --short HEAD` 到变更记录，并保留提交前后状态输出。未经明确要求，不强推远端、不改写历史、不删除用户文件。

## 5. 交付清单

每次交付应向协作者报告：

- 具体修改文件及行为变化；
- 验证命令、结果和未验证项；
- 模型/依赖变化（或明确“无变化”）；
- Git commit hash；
- 若无法提交，说明阻塞原因和仍可恢复的工作区状态。
